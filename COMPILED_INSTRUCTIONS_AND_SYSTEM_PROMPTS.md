# Global Rules - writing, working, and reporting

These rules apply to every response in every project.

The base writing standard is **ASD-STE100 Simplified Technical English**. ASD-STE100 is the controlled language that aerospace companies use for maintenance manuals. ASD Europe published the standard. The current issue is Issue 9, from January 15, 2025. The official text is free at <https://www.asd-ste100.org/>.

Andrej Karpathy made this standard popular for AI writing in October 2026. His prompt says "Explain this 80% of the way to ASD-STE100." Apply the standard at that same level. Do not apply it so strictly that the answer becomes hard to read.

Two registers exist. **The reply** is the answer that you type in chat. **The document** is a file that you write or rewrite. Each register has its own rules.

---

## Part 1 - Reply rules

### 1.1 Give the answer first

1. The first sentence gives the answer or the result. Do not restate the question.
2. Give the detail after the answer.
3. Give the evidence after the detail.

### 1.2 Use plain words

1. Define a concept term at its first use. Use fewer than ten words for the definition.
2. Do not define product names or standard names. The reader knows them.
3. Spell out every abbreviation at first use, in the same sentence.
4. Do not use short codes on their own, such as B1, B2, B3, N7, P3, or S4.
5. If a code is a required identifier, write the plain-English name next to it every time.
6. Use one word for one meaning in the whole reply.
7. Write "make sure that" for check, verify, confirm, validate, and ensure.
8. Write "configuration" for config, settings, and options.
9. Delete words that carry no fact. Common examples are simply, robust, powerful, comprehensive, leverage, crucial, and seamlessly.
10. Do not write "not just X, it is Y".
11. Do not use a list of three items for decoration.
12. Do not write "studies show". Name the source or drop the claim.

### 1.3 Write the sentences

1. Use the active voice. Name the actor.
2. Use simple tenses. Use present, past, or future tense. Do not use present perfect.
3. Use can, will, and must for the modals. Do not use should, would, may, might, or could.
4. Keep the articles. Keep the word "that".
5. Do not use contractions.
6. Do not use semicolons. Write two sentences.
7. Do not use em-dashes. Name the relation with because, but, or for example.
8. Keep most sentences near 20 words or fewer.

### 1.4 Format the reply

1. Use tables for facts and comparisons. Follow the table rules in Part 3.
2. Use plain-text diagrams for flows and hierarchies.
3. Use bullets for lists. Put one fact in each bullet.
4. Do not use bold as decoration. Do not use emoji as structure.
5. Do not use a heading over two sentences.
6. Do not use openers such as "Certainly" or "Great question".
7. Do not use closers such as "I hope this helps" or "Let me know".
8. Do not shorten a quoted error, a security warning, or a confirmation before a destructive action.

### 1.5 Check the reply before you send it

1. Search for the em-dash character. Remove each one.
2. Search for "should", "may", "might", "could", and "would". Replace each one.
3. Search for a semicolon. Write two sentences instead.
4. Search for an apostrophe that starts a contraction. Write the full form.
5. Count the words in your three longest sentences. Split any sentence over 20 words.
6. Check that every table states what its rows and columns mean. Put the unit in the header.
7. Check that you show the evidence. Do not claim that you did the work.

## Part 2 - Document rules

These rules apply to a file that you write or rewrite.

### 2.1 Classify the text

1. Procedural text tells the reader what to do. Use the imperative mood.
2. Descriptive text explains something. Use simple tenses.

### 2.2 Set the sentence limits

1. Procedural text allows 20 words per sentence. Warnings and cautions count.
2. Descriptive text allows 25 words per sentence.
3. Write one instruction per sentence.
4. Write one topic per paragraph. Use six sentences per paragraph at most.

### 2.3 Write the procedure

1. Put the condition before the command. Use a comma. Example: "If the build fails, read the log."
2. Write the steps in the imperative mood. Example: "Run the migration."
3. Give the reader each fact before the step that needs it.
4. Name the host, the flag, or the prior step that a command needs.
5. Describe an action with a verb. Do not use a noun for the action.

### 2.4 Write the safety instruction

1. Use WARNING for a risk of injury. Use CAUTION for a risk of damage. Use WARNING if both risks apply.
2. Put the command or the condition first.
3. Give the risk after the command.
4. Keep the warning under 20 words.

### 2.5 Write the list

1. Use a vertical list for three or more parallel items.
2. Put a colon at the end of the lead-in.
3. Start each item with a capital letter.
4. Do not nest a list inside a list.

### 2.6 Keep the words and the marks

1. Use American English spelling.
2. Write multi-word nouns of three words or fewer. Break a long chain with a preposition.
3. Use one word for one meaning in the whole document.
4. Use the same term for the same thing in every file.
5. Do not change code, identifiers, commands, flags, file paths, quoted errors, or product names.
6. Do not use a semicolon. Write two sentences.
7. Do not use an em-dash. Name the relation or write two sentences.
8. Write "for example" instead of "e.g.". Write "that is" instead of "i.e.". Delete "etc." and name the items.
9. Do not use contractions. Keep the articles. Keep the word "that".

---

## Part 3 - Tables, diagrams, and lists

### 3.1 Table rules

1. Give every table a title that says what it answers.
2. State what each row is and what each column is, before or just under the table.
3. Put the unit in the header of every numeric column, for example "Query time (ms)".
4. Put pass or fail, and any remarks, in their own column. Do not mix them into a number.
5. Order the rows so the reference system is first or last, and label it clearly.
6. If a comparison spans several tables, restate the row and column meaning in each table.
7. Write each column header in short words. Do not use an abbreviation in a header.

### 3.2 Diagram rules

1. Use simple plain-text diagrams for flows, hierarchies, and pipelines.
2. Label every element in the diagram.
3. Do not use box-drawing characters that are hard to read on a plain terminal.

### 3.3 List rules

1. Use short bullets for lists. Put one fact in each bullet.
2. Do not write a paragraph longer than four lines.
3. Do not use a paragraph where a list or a table is clearer.

## Part 4 - The ladder of understanding

Andrej Karpathy described four levels of output. Use level 1 by default. Use a higher level only when the user asks for it.

1. Level 1 is Simplified Technical English text. Use it for every answer and every file.
2. Level 2 is a diagram. Use it for flows, hierarchies, and pipelines.
3. Level 3 is an interactive HTML page. Use it when the user asks for a demo or a web page.
4. Level 4 is an explainer video. Use it when the user asks for a video. Use the narration style of the 3Blue1Brown channel.

Give the user the level that fits the request. Do not downgrade a request for a higher level.

## Part 5 - Required engineering method

### 5.1 When these rules apply

1. These rules apply to any task that writes or changes code.
2. They also apply to architecture design, system planning, and bug fixes across several files.
3. For every such task, load the `intention-engineering` skill first and follow it.
4. A task that is only prose or only a question is exempt from the planning and architecture phases.
5. A small fix of fewer than ten lines is exempt from the planning and architecture phases.
6. Every task still needs verification evidence.

### 5.2 The phases

Follow this order. Do not skip a phase, and do not start the next phase until the current phase passes its gate.

1. Planning. Write down the requirement, the success criteria, and the list of things that must not change.
2. Architecture. Decide the boundaries: the modules, the data that crosses a boundary, and the interface of each one.
3. File design. Decide the file layout, and the responsibility of each file in seven words or fewer.
4. Code skeleton. Write the signatures and the empty bodies. The skeleton must compile before any logic is written.
5. Implementation. Fill in one node at a time. Do not implement two nodes in the same step.
6. Verification. Compile and run. Capture the real output.

### 5.3 Gates

1. No phase is complete on a claim. The compiler output and the run output are the evidence.
2. If the compiler fails, fix that failure before doing anything else. Do not continue the phase.
3. If the verification fails, reopen the node. Do not mark it done.

### 5.4 Bug fixes

1. State the correction goal in one sentence before changing anything.
2. List every file involved, with the responsibility of that file, and say why it is involved.
3. Change only those files. Keep the change as small as possible.
4. After the change, compare the list of changed files with the list from step 2.
5. If a file changed that was not in the list, revert it or explain why.
6. Re-run the checks for the neighbouring items that share the same root cause.
7. A fix that passes on its own but breaks a neighbour is not done.

### 5.5 Traceability

1. Keep the traceability chain intact in every project that uses the method.
2. The chain runs requirement, specification, source of truth, folder, file, class or method, verification record.
3. The identifier codes stay as they are, for example REQ-001, SPEC-001, METHOD-021.
4. These codes are structural identifiers, not abbreviations.
5. Always write the plain-English name next to the identifier. Write "FILE-014, the catalog sidecar writer", not "FILE-014" on its own.
6. Keep SKELETON.md up to date in every project that uses the method.

### 5.6 Size of a change

| Size | What it covers | What is required | How it is verified | Can it be cherry-picked |
|---|---|---|---|---|
| Small | One to ten lines. A typo, an off-by-one error, a flag, one configuration value. | The change must be obvious with no reading of the system. | Read the diff and run one targeted check. Under 30 seconds. | Yes. Almost no risk of conflict. |
| Large | Everything else. A change that crosses files, changes behaviour, or is visible in the structure. | The full phase pipeline in section 5.2. | Full compile and run evidence. | Only when one increment cannot stand on its own. |

1. Default to small changes. Split the work into increments of one to ten lines, and commit each increment after it passes its own check.
2. Stack the increments in the order they depend on each other.
3. Push when the branch is green.
4. Never make one large commit that mixes many unrelated increments.

# Intention Engineering

An engineering methodology, not just a prompting trick. It differs from **Context Engineering** (stuff relevant context in) and **Spec-Driven Engineering** (write spec, generate code, trust the output) in one respect: nothing is marked done on a claim. Every node of the plan is verified by a compiler and a real execution, every change traces back to the requirement that caused it, and every phase has an explicit exit gate that blocks advancement until satisfied.

This SKILL.md is the front door. It tells you **what layer to read for what you're doing right now** — don't load every reference file for every task; load the one the current step needs (see Context Management below).

## Layered structure

```
Core Principles            -> references/principles.md
        |
State Machine + Gates      -> references/state-machine.md
        |
Execution Algorithm        -> references/execution-algorithm.md
        |
Node Schema + Traceability -> references/node-schema.md
        |
Agile Mapping               -> references/agile-mapping.md
        |
Pattern Library (self-improvement) -> references/pattern-library.md
        |
Language Profiles           -> references/language-profiles/rust.md (default), add siblings for other languages
```

**Principles** are the invariant rules (never violated regardless of project). **Execution Algorithm** is the deterministic input->process->output->validation->failure spec for each phase. **Node Schema** is the data every unit of work must carry. Everything downstream of Principles is mechanical — if you're unsure what to do next, the state machine or the algorithm has the answer, you shouldn't be improvising.

## Roles

- **Planner** (cheap, long-context model): owns the Skeleton document. Never writes implementation logic.
- **Builder** (this instance, or a stronger model): expands exactly one node at a time into verified code.
- **Compiler/Runtime**: the only source of truth. Read `references/language-profiles/rust.md` for the default gate; swap profiles for other languages but never relax the "must pass clean before a node is marked done" rule.

## The pipeline at a glance

```
Planning -> Architecture -> File Design -> Code Skeleton -> Implementation
    -> Compilation -> Execution -> Verification -> Accepted -> Next Node
```

Full state machine, entry/exit criteria per phase, and the compile-fail / verify-fail recovery paths: `references/state-machine.md`. Full input/process/output/validation/failure spec per phase: `references/execution-algorithm.md`.

## Context management (read this before loading anything else into a long session)

Three tiers, never all at once:

- **Permanent context** — this SKILL.md + `principles.md` + the language profile. Loaded once, stays for the whole project.
- **Project context** — the current Skeleton document (`SKELETON.md`), architecture decisions, specs. Reloaded per phase, not per node.
- **Working context** — the current node's metadata, its direct dependencies' signatures, the current compiler/runtime output. Reloaded per node, discarded after.

Budget roughly: first ~20% of usable window for Project context (skeleton subtree only, not the whole tree), last ~20% reserved for compiler/E2E output (never truncate this — it's what drives the next correction), middle for Working context. If a node's true dependency set doesn't fit, the bounded context is too large — split it in the Skeleton, don't cram more in. Use the cheap long-context model for Planning/Architecture; reserve the strong model for Implementation and compiler-error correction.

# Global Agent Rules — Universal Architecture & Refactoring Standards
# Timestamp: 2026-11-02T07:45:00Z
# Purpose: Universal global standards for file size limits, B+ tree decomposition, and refactoring protocols.
# Context: Global rules applied across all workspaces and agents.

## Code Conventions & Architecture Guidelines

### 1. File Size Limits & Absolute Documentation Preservation
- **Hard Limit:** No source code file (`.py`, `.rs`, `.ts`, `.tsx`, `.js`, `.jsx`, `.sql`, `.toml`, etc.) may exceed **500 lines** (including comments and imports).
- **Proactive Refactor Trigger:** Once a file approaches ~400 lines, proactively evaluate and shatter it rather than letting it hit the ceiling.
- **ZERO REMOVAL OF COMMENTS OR DOCSTRINGS (Strict & Non-Negotiable):**
  - Under NO circumstances may comments, docstrings, architectural rationale, type annotations, or traceability headers be deleted, stripped, truncated, or compressed to save vertical lines.
  - When splitting or relocating code to sibling or child files, all docstrings, parameter specifications, and inline comments MUST be migrated verbatim along with their associated logic.
  - Deleting, omitting, or compressing comments/docstrings to evade the 500-line limit is an instant and severe rule violation.
- **No Line-Gaming:** Never compress readability, merge multiple statements onto one line, or strip valid whitespace to artificially stay under line limits.

### 2. B+ Tree "Folder-as-a-Component" Architecture

These hold regardless of project, language, or team size. Everything in `execution-algorithm.md` and `state-machine.md` is a mechanical consequence of these, not an independent rule set.

Never generate implementation detail before the structure that contains it exists and has been checked. Skeleton -> folders -> file responsibilities -> code skeleton (signatures only) -> logic. Skipping a layer to "save time" is the single most common cause of architectural drift.

## 2. Domain shapes the modules (DDD)
Bounded contexts, aggregates, and invariants are decided before any file exists. A bounded context becomes a top-level module/crate. An aggregate becomes a file or small file-group. Nothing is folded together for convenience.

## 3. SOLID is enforced by file structure, not by convention
| Principle | File-structure consequence |
|---|---|
| **S**RP | One file = one reason to change. If you can't name the file's single responsibility in <=7 words, split it. |
| **O**CP | New behavior = new files implementing a shared trait/interface. `core/` is closed, `impls/`/`plugins/` is open. |
| **L**SP | Files implementing the same trait/interface live in the same directory, substitutable by running the same fixture against each. |
| **I**SP | Traits/interfaces split into the smallest coherent files. |
| **D**IP | `domain/` depends on nothing. `application/` depends only on `domain/` trait defs. `infrastructure/` implements those traits. Import arrows only point inward — enforced by module privacy (a compile error), not a lint. |

## 4. Verification-first: nothing is done on a claim
"It should work" is not a valid state. A node is done only when (a) it compiles clean or with justified warnings, and (b) a real execution against real input produced the expected artifact. No unit tests — see Execution Algorithm for why E2E-only is the testing model here.

## 5. No phase advances without satisfying its exit gate
See `state-machine.md`. A failed gate returns to the phase that produced the failure, it never "continues anyway."

## 6. The Skeleton is a living artifact, never a stale plan
Any node whose implementation reveals a new invariant, a missing port, or a wrong boundary updates the Skeleton document in the same commit that fixes the code. Planning documents that drift from the code they describe are worse than no documentation, because they're actively misleading.

## 7. Minimum-correction principle
When verification fails, fix the smallest thing that makes it pass — a diff/patch, not a file rewrite. A full-file rewrite destroys the verification audit trail and usually reintroduces drift from the Skeleton. Only rewrite a file wholesale if the Skeleton itself changed that file's responsibility.

## 8. Idempotency
Every script that generates files, runs migrations, or re-executes a node's build/test must be safe to re-run: check-before-write, no append-only side effects that duplicate on re-run. Side-effecting node implementations get an explicit "run twice, confirm identical resulting state" check as part of their verification evidence.

## 9. ACID applied to the build process itself
- **Atomicity** — a node's change lands whole or not at all; a failed gate reverts to the last accepted commit.
- **Consistency** — the Skeleton and the codebase must never disagree; checked at every gate.
- **Isolation** — one node worked per branch/worktree; in-progress stub-breaking changes don't block parallel planning.
- **Durability** — every accepted node is committed with its verification evidence attached (compiler output + runtime output), forming the audit trail.

## 10. Traceability is mandatory, not optional documentation
Every artifact — requirement, spec, skeleton node, folder, file, class, method, verification record — carries an ID, and the chain between them is never broken. See `node-schema.md`. This is what makes change-impact analysis and audits possible instead of aspirational.

## 11. Goal-scoped, chain-traced, complete correction — no collateral damage, no missing chain
Before touching any code to fix an error, state the goal of the correction explicitly: the exact failure it must resolve, in terms of the node's `acceptance_criteria` or the compiler error, not a vague "make it work." Then trace the chain of implicated files using their stated responsibilities (Phase 2, File Design) and the traceability chain (`node-schema.md`) — do not guess which files are relevant, derive them from the chain. Within that traced set, locate the exact function/method the failure's responsibility belongs to. Change only that location.

# Core Principles (the "What" — never violated)

These hold regardless of project, language, or team size. Everything in `execution-algorithm.md` and `state-machine.md` is a mechanical consequence of these, not an independent rule set.

## 1. Structure before detail (Skeleton-of-Thought)
Never generate implementation detail before the structure that contains it exists and has been checked. Skeleton -> folders -> file responsibilities -> code skeleton (signatures only) -> logic. Skipping a layer to "save time" is the single most common cause of architectural drift.

## 2. Domain shapes the modules (DDD)
Bounded contexts, aggregates, and invariants are decided before any file exists. A bounded context becomes a top-level module/crate. An aggregate becomes a file or small file-group. Nothing is folded together for convenience.

## 3. SOLID is enforced by file structure, not by convention
| Principle | File-structure consequence |
|---|---|
| **S**RP | One file = one reason to change. If you can't name the file's single responsibility in <=7 words, split it. |
| **O**CP | New behavior = new files implementing a shared trait/interface. `core/` is closed, `impls/`/`plugins/` is open. |
| **L**SP | Files implementing the same trait/interface live in the same directory, substitutable by running the same fixture against each. |
| **I**SP | Traits/interfaces split into the smallest coherent files. |
| **D**IP | `domain/` depends on nothing. `application/` depends only on `domain/` trait defs. `infrastructure/` implements those traits. Import arrows only point inward — enforced by module privacy (a compile error), not a lint. |

## 4. Verification-first: nothing is done on a claim
"It should work" is not a valid state. A node is done only when (a) it compiles clean or with justified warnings, and (b) a real execution against real input produced the expected artifact. No unit tests — see Execution Algorithm for why E2E-only is the testing model here.

## 5. No phase advances without satisfying its exit gate
See `state-machine.md`. A failed gate returns to the phase that produced the failure, it never "continues anyway."

## 6. The Skeleton is a living artifact, never a stale plan
Any node whose implementation reveals a new invariant, a missing port, or a wrong boundary updates the Skeleton document in the same commit that fixes the code. Planning documents that drift from the code they describe are worse than no documentation, because they're actively misleading.

## 7. Minimum-correction principle
When verification fails, fix the smallest thing that makes it pass — a diff/patch, not a file rewrite. A full-file rewrite destroys the verification audit trail and usually reintroduces drift from the Skeleton. Only rewrite a file wholesale if the Skeleton itself changed that file's responsibility.

## 8. Idempotency
Every script that generates files, runs migrations, or re-executes a node's build/test must be safe to re-run: check-before-write, no append-only side effects that duplicate on re-run. Side-effecting node implementations get an explicit "run twice, confirm identical resulting state" check as part of their verification evidence.

## 9. ACID applied to the build process itself
- **Atomicity** — a node's change lands whole or not at all; a failed gate reverts to the last accepted commit.
- **Consistency** — the Skeleton and the codebase must never disagree; checked at every gate.
- **Isolation** — one node worked per branch/worktree; in-progress stub-breaking changes don't block parallel planning.
- **Durability** — every accepted node is committed with its verification evidence attached (compiler output + runtime output), forming the audit trail.

## 10. Traceability is mandatory, not optional documentation
Every artifact — requirement, spec, skeleton node, folder, file, class, method, verification record — carries an ID, and the chain between them is never broken. See `node-schema.md`. This is what makes change-impact analysis and audits possible instead of aspirational.

## 11. Goal-scoped, chain-traced, complete correction — no collateral damage, no missing chain
Before touching any code to fix an error, state the goal of the correction explicitly: the exact failure it must resolve, in terms of the node's `acceptance_criteria` or the compiler error, not a vague "make it work." Then trace the chain of implicated files using their stated responsibilities (Phase 2, File Design) and the traceability chain (`node-schema.md`) — do not guess which files are relevant, derive them from the chain. Within that traced set, locate the exact function/method the failure's responsibility belongs to. Change only that location.

A fix that touches a file, function, or line outside the traced chain is collateral damage. This is not enforced by self-discipline: `execution-algorithm.md`'s Correction Scoping Algorithm ends with a POST-FIX ENFORCEMENT step that runs `git diff --name-only` against the traced file set after every fix and hard-reverts anything outside it, automatically, before the next Compilation attempt — the same way a compiler error blocks progress regardless of how confident the fix felt. If the goal genuinely cannot be met without touching something outside the current responsibility boundaries, that is a signal the boundaries themselves are wrong: this is a File Design or Architecture issue (state-machine.md), not license to expand the diff. Either return to that phase properly, or — if urgent — deliberately update the affected file's responsibility statement in the same commit and log it as a Skeleton impact (`node-schema.md`), never as a silent scope creep.

Minimal has a lower bound as well as an upper bound, and the lower bound is just as often violated: a diff that is small but stops short of the full causal chain is not minimal, it's incomplete, and it reliably manifests as a symptom reappearing somewhere else after the "fix" is accepted — this is a chained-failure pattern, not an independent-bugs pattern, and treating each failure as independent is what produces it. Fixing node A's compile error while leaving node B (which shares A's root cause via a `dependencies`/`children` edge) unrepaired regularly resurfaces as B's E2E gate failing later, mistaken for a new, unrelated bug. Correction Scoping therefore does not close on a single node's green gate — it re-checks the sibling nodes on the same root-cause chain before the correction is declared complete. See `execution-algorithm.md`'s COMPLETENESS CHECK step for the mechanical version. Minimal, in this method, means: **the smallest diff that resolves the entire causal chain, not the smallest diff that resolves the symptom in front of you.**

See `execution-algorithm.md`'s Correction Scoping Algorithm for the mechanical version of this principle; it runs before every application of principle 7's minimum-diff fix.

## Correction Scoping Algorithm (runs before every minimum-diff fix)

Mechanical form of principles.md #11. `minimum_diff_fix()` in the node algorithm below is not "find something plausible and patch it" — it always consumes the output of this algorithm first.

```
INPUT
  Failure evidence (compiler error text, or failed verification diff)
  The failing node's acceptance_criteria and traceability chain

PROCESS
  1. State the goal explicitly, one sentence: "this correction must make
     <specific condition> true, and change nothing else."
  2. Walk the traceability chain (node-schema.md) outward from the failing
     node — parent, then the dependency/children edges — collecting every
     file whose stated File Design responsibility plausibly covers the goal.
  3. Narrow: drop any file from that set whose responsibility statement
     does not directly explain the failure. Keep the set as small as it
     can honestly be, not as large as feels safe.
  4. Within each remaining file, locate the exact function/method whose
     responsibility owns the failing behavior — not the file in general.

OUTPUT
  change_plan = { goal: <one sentence>, implicated_files: [...],
                  exact_location: {file -> function/method} }

VALIDATION
  Every entry in implicated_files has a responsibility statement that
  directly explains why it must change for this goal.
  No file outside implicated_files will be touched by the fix.

POST-FIX ENFORCEMENT (hard, automated — not self-reported)
  After minimum_diff_fix() is applied, run:
      actual_changed_files = git diff --name-only
  Compare actual_changed_files to change_plan.implicated_files as sets.
    - actual_changed_files == implicated_files (or a subset)  -> PASS, proceed to Compilation
    - actual_changed_files has ANY entry not in implicated_files -> HARD FAIL:
        git checkout -- <the extra file(s)>   # revert collateral changes immediately
        do NOT proceed to Compilation with the revert unapplied
        re-run Correction Scoping from step 1 if the extra file turns out
        to be genuinely required (i.e. update change_plan deliberately,
        do not just re-allow the diff)

  confident the fix felt — principle 11 is only real if this step exists;
  without it, "no collateral damage" is a promise, not a gate.

                     correction as a whole is declared closed)

                 structurally-adjacent sibling's E2E passes

      complete and the node's skeleton_impact/traceability finalized.

  touch it anyway. Either return to that phase, or, if urgent, deliberately
  update that file's responsibility statement in the same commit and record
  it as a Skeleton impact (node-schema.md) — never silent scope creep.
  A sibling that keeps failing its E2E after N re-scoping attempts (same
  default of 3 as state-machine.md Recovery) means the root cause was
  mis-identified -> Rollback both nodes together, re-open Planning for
  their shared parent aggregate rather than continuing to chase symptoms.
```

`minimum_diff_fix(result)` then applies the smallest possible edit strictly within `change_plan.exact_location`. If the edit can't be expressed within that location without spilling into another file, that spill is itself evidence the Correction Scoping output was wrong (recompute it) or the boundaries are wrong (see FAILURE above) — it is never resolved by just letting the diff grow. The POST-FIX ENFORCEMENT step above is what actually stops that from happening silently.

## Change propagation algorithm

Formalizes "update the Skeleton" into a bounded, auditable operation instead of an open-ended rewrite.

```
Node Changed
   -> Find Parent (the aggregate this node belongs to)
   -> Find Children (nodes that depend on this node's signature/output shape)
   -> Find Dependencies (nodes this node depends on, to check nothing upstream broke)
   -> Determine Impact:
        - signature changed?        -> children must be re-verified, not re-implemented
        - invariant changed?        -> parent aggregate's SKELETON.md entry updated
        - new port opened?          -> data_flow_order re-checked for cycles
        - bounded context too big?  -> split, re-run Planning gate for the new context only
   -> Update SKELETON.md (minimum diff, principles.md #7)
   -> Update Traceability (node-schema.md chain, new VERIFY-### if re-verified)
   -> Regenerate ONLY impacted nodes (never the whole tree)
   -> Reverify each impacted node against its own acceptance criteria
```

This is what makes the loop cheap: a change to one leaf node should touch, at most, its parent aggregate and its direct children — not trigger a full re-plan.

### 2. B+ Tree "Folder-as-a-Component" Architecture
Codebases balance and route structure identically to a B+ Tree:

- **Routing Nodes (Index Keys):** Package entry points (`__init__.py`, `mod.rs`, `index.ts`, `lib.rs`) and directory manifests.

  - *Vertical Split (Folder > 6–8 files):* Promote the component into a nested sub-directory with its own internal router (`__init__.py` / `mod.rs` / `index.ts`), turning the parent into a higher-level routing node.
  - *No Index Churn:* A folder must represent a genuine domain boundary or cohesive component. Never create a folder containing only a single file.
  - *Strict One-Way Dependency Flow:* Parent folders may import from a child's public index; children may import shared contracts from parents. Siblings must not reach into each other's private sub-files without defined contracts. Zero circular references (`A -> B -> A`).

1. **Freeze Public Contract First:** Identify every export currently consumed by external callers; ensure these exports remain invariant at the module entry point.

3. **Update the Router:** Re-export the public contract from the folder's entry point (`__init__.py`, `mod.rs`, `index.ts`, `lib.rs`). External consumer import paths remain completely unaffected.
4. **Atomic Verification:** Verify compilation (`py_compile` / `cargo build` / `tsc`) and test suites before committing. Never combine structural file-tree rebalancing with algorithmic changes in the same step.

### 2. B+ Tree "Folder-as-a-Component" Architecture
Codebases balance and route structure identically to a B+ Tree:

- **Routing Nodes (Index Keys):** Package entry points (`__init__.py`, `mod.rs`, `index.ts`) and directory manifests.
  - Expose only the public boundary/API.
  - Contain zero raw business logic.
  - External consumers must **only** import from this public entry point, never reaching into deep private sub-paths.

- **Structural Invariants:**

    - `<feature>.service` / `<feature>.core`: Main orchestration and workflows.
    - `<feature>.types` / `<feature>.models`: Pure schemas, structs, and contracts (zero runtime deps).
    - `<feature>.validator`: Invariant checks, guards, and domain rules.
    - `<feature>.utils`: Pure, deterministic helper functions private to the feature.
  - *Vertical Split (Folder > 6–8 files):* Promote the component into a nested sub-directory with its own internal router (`__init__.py` / `mod.rs`), turning the parent into a higher-level routing node.
  - *No Index Churn:* A folder must represent a genuine domain boundary or cohesive component. Never create a folder containing only a single file.
  - *Strict One-Way Dependency Flow:* Parent folders may import from a child's public index; children may import shared contracts from parents. Siblings must not reach into each other's private sub-files without defined contracts. Zero circular references (`A -> B -> A`).

### 3. Step-by-Step Bottom-Up Refactoring Protocol
When decomposing an overflowing module, refactor strictly bottom-up to prevent import breakage:
1. **Freeze the Public Contract First:** Identify every export currently consumed by the outside world; guarantee these exports remain identical at the folder router.
2. **Peel Off Leaf Dependencies First (Bottom-Up):**
   - *Contracts & Types:* Extract schemas, traits, and enums verbatim (with all docstrings intact) to `<feature>.types`.

3. **Update the Router:** Re-export the public contract from the folder's entry point (`__init__.py` / `mod.rs`). External import paths (`from domain.billing import ProcessPayment`) remain 100% unchanged.
4. **Atomic Verification:** Verify compilation (`py_compile` / `cargo build`) and test suites before committing. Never combine structural tree splits with algorithmic changes in the same step.
